# 0068. Unified, extensible elliptic-curve catalog

- **Status:** Accepted
- **Date:** 2026-10-11
- **Deciders:** NCode.Identity maintainers

## Context

Elliptic-curve knowledge lived in two disconnected, size-keyed places:

- key **generation** hard-coded a `bits → ECCurve` switch (`256 → nistP256`, `384 → nistP384`,
  `521 → nistP521`) inside the secret generator, so only the three NIST P-curves could ever be
  generated and the set was not extensible;
- **JWK publication** had a separate `IEccCurveSpecificationRegistry` in the authentication/JWKS layer,
  also keyed by **size**, that named a key's `crv` from its bit length.

Keying by size is fundamentally ambiguous: two distinct curves can share a size (for example
`secp256k1` and `P-256`/`secp256r1` are both 256-bit), so a size-keyed registry cannot generate a
chosen same-size curve and would mis-name a non-NIST key's `crv`. The two registries could also drift
from each other.

## Decision

Unify elliptic curves into one extensible core catalog and select curves by **identity**, not size.

- `IEccCurveCatalog` (core `NCode.Identity.Secrets`) is the single source of truth. An
  `EccCurveSpecification` carries the `crv` name, the size in bits, and the underlying `ECCurve`. The
  default catalog seeds the NIST P-curves and merges in any application-registered
  `EccCurveSpecification` services; lookups are by name, by size (the back-compatible default), and by
  the key's **actual** `ECCurve` (named-curve OID) so a deserialized key names its `crv` unambiguously.
- Key generation flows through a growable `SecretKeyGenerationParameters { KeySizeBits, Curve? }`:
  `ISecretKeyTypeDescriptor.GenerateKeyMaterial`/`ValidateGeneration` take it in place of a bare key
  size. The ECC descriptor resolves the requested curve by name, or by size when no curve is given;
  non-ECC descriptors reject a curve. A `curve` field is threaded end-to-end through
  `CreateSecretRequest` → `GenerateSecretRequest` → the descriptor.
- The authentication-layer `IEccCurveSpecificationRegistry`/`EccCurveSpecification`/
  `DefaultEccCurveSpecificationRegistry` are **removed**; the ECC secret-key-type descriptor's JWK export
  (`ISecretKeyTypeDescriptor.ExportPublicKey`, [ADR-0105](0105-secret-key-type-descriptor-first-class-seam.md))
  consumes the core catalog, resolving `crv` by the key's actual curve (falling back to size). There is now one curve
  registry, shared by generation and publication.
- The capabilities document ([ADR-0067](0067-secret-type-capability-catalog-and-capabilities-discovery.md))
  gains an `eccCurves` section (its own provider), and the management console offers a server-driven
  curve picker on the create-secret form when `ecc` is selected.

## Consequences

- Any curve can be supported by registering one `EccCurveSpecification`; it is immediately available to
  generation, validation, JWK publication, and the console picker.
- Same-size curves are disambiguated: a chosen curve is generated by name, and a key's `crv` is named
  from its actual curve rather than guessed from its size.
- Generation and JWK naming can no longer drift — they read the same catalog.
- Public API churn is expected per [ADR-0025](0025-pre-release-posture-and-auth0-parity-plus.md): the
  JWKS curve types are removed from the authentication abstractions and replaced by the core catalog,
  and `CreateSecretRequest`/`GenerateSecretRequest` gain a `curve` field.
