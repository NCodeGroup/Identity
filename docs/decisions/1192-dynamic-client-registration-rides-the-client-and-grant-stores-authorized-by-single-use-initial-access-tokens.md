# 1192. Dynamic client registration rides the client and grant stores, authorized by single-use initial access tokens

- **Status:** Accepted
- **Date:** 2026-10-20
- **Deciders:** NCode Group

## Context

[RFC 7591](https://www.rfc-editor.org/rfc/rfc7591) lets a client register itself by `POST`ing a JSON client-metadata
document to a `registration_endpoint` and receiving a `client_id`, an optional `client_secret`, and, with
[RFC 7592](https://www.rfc-editor.org/rfc/rfc7592), a `registration_access_token` and a `registration_client_uri` that
it uses to read, update and delete its own registration. It is the Dynamic OP certification profile, and without it the
only way to create a client is the management API or provisioning.

The server already has every seam the feature needs. A `PersistedClient` (a disabled flag, a settings document and a
secret collection) is stored through `IClientStore`. Client secrets are generated by `ISecretGenerator` and revealed
once ([ADR-1050](1050-a-secret-is-generated-by-the-server-revealed-once-and-never-cached.md)). Protocol endpoints register themselves and
advertise themselves in discovery
([ADR-1086](1086-endpoints-compose-as-a-declarative-group-tree-and-a-protocol-endpoint-is-a-thin-mediator-driven-provider.md)).
Settings cascade server, tenant, client through a merge lattice
([ADR-1010](1010-settings-merge-as-ceilings-and-floors-unset-lists-restrict-nothing-and-a-secure-baseline-supplies-defaults.md)).
`IPersistedGrantService` persists a tenant-scoped, hash-keyed, optionally expiring, status-bearing grant envelope.

Three questions need a decision:

1. **Who may register?** RFC 7591 permits open registration and registration gated by an initial access token. Open
   registration is an abuse vector, while the conformance harness wants to provision clients unattended.
2. **How is the per-client `registration_access_token` stored and authenticated?** It is a long-lived bearer bound to
   one client and presented without a `client_id`, which is not standard client authentication.
3. **How does a registrant prove it may act for a resource server?** A resource server introspects through a client
   bound to it, a resource-server client
   ([ADR-1168](1168-introspection-reports-a-token-active-only-to-the-party-that-consumes-it.md)), and such a client reads
   every access token issued for that resource server. Binding one is a change to the resource server, so the caller
   must be authorized to update it. [RFC 9701](https://www.rfc-editor.org/rfc/rfc9701) §3 lets an authorization server
   register resource servers dynamically, and a deployment that provisions its APIs automatically needs a pipeline to
   create the resource server and have the API register its own introspection client without a management credential
   at run time. RFC 7591 has no member that names a resource server, and an open request proves nothing.

## Decision

**Dynamic registration is one self-advertising endpoint family in the authentication library. It writes a
`PersistedClient` through the client store, reveals the secret through the one-time secret generator, and models the
`registration_access_token` and the initial access token as persisted-grant payloads. An initial access token is
single-use and short-lived, and it can name the resource server whose introspection client its one registration
creates.** No table, store or migration is added.

### Endpoints

- `POST /oauth2/register` is the registration endpoint (RFC 7591), advertised as `registration_endpoint` in
  `.well-known/openid-configuration`.
- `GET`, `PUT` and `DELETE /oauth2/register/{client_id}` are the per-client management endpoint (RFC 7592). It is not
  discoverable: a client reaches it through the `registration_client_uri` returned at registration.

### Metadata

- Registration writes a `PersistedClient` through `IClientStore`. Every metadata member is a client setting under its RFC
  name ([ADR-1139](1139-setting-names-are-a-closed-vocabulary-changed-outright-and-settings-the-server-cannot-honor-fail-loudly.md)),
  so the settings document holds no untyped keys. The requested `scope` is not stored: the response reports the scopes
  the client may request. A `GET` rebuilds the client information response from the settings.
- `token_endpoint_auth_method` defaults to `client_secret_basic` and must be a registered method within the tenant's
  `token_endpoint_auth_methods_supported`
  ([ADR-1145](1145-a-client-authenticates-only-with-its-registered-method-which-a-registered-descriptor-names.md)).
- `response_types` and `grant_types` follow
  [ADR-1141](1141-a-response-type-is-a-whole-value-and-the-listed-values-alone-control-front-channel-tokens.md), and
  redirect URIs and their kinds follow [ADR-1203](1203-redirect-uris-are-matched-exactly-as-written-and-their-kinds-are-narrowed-by-settings.md).
- `jwks` is imported under the client-key policy
  ([ADR-1161](1161-every-owners-public-keys-have-one-source-and-are-imported-under-one-key-policy.md)).
- `subject_type` and `sector_identifier_uri` follow
  [ADR-1093](1093-a-pairwise-subject-is-a-one-way-projection-of-the-principal-over-a-verified-sector.md).
- Logout metadata is stored as the client settings of the same names, which the back-channel notifier, the end-session
  endpoint and the front-channel logout service read, and is reported back:
  - `backchannel_logout_uri` must be an absolute `https` URI without a fragment, because a `logout_token` must not
    travel in clear.
  - `post_logout_redirect_uris` must be absolute URIs without a fragment.
  - `frontchannel_logout_uri` must be an absolute URI without a fragment whose scheme, host and port are those of a
    registered redirect URI.
  - A logout channel the tenant does not support fails the client coherence rules.
- Failures answer with the RFC 7591 codes `invalid_client_metadata` and `invalid_redirect_uri`.

### Secrets and registration access tokens

- A confidential client receives a server-generated secret from `ISecretGenerator`, revealed once as `client_secret`
  with `client_secret_expires_at: 0`. It is the secret the client presents for `client_secret_basic` and
  `client_secret_post`. A public client (`none`) receives none.
- The `registration_access_token` is a non-expiring `PersistedGrant` keyed by a salted hash of the token, so the
  plaintext is never stored. Its payload binds the `client_id`. An RFC 7592 call looks the bearer up as that grant and
  matches the payload to the route's `{client_id}`. `GET` and `PUT` neither return nor rotate it, because the server
  holds only its hash; RFC 7592 makes rotation a MAY.
- `DELETE` removes the client with its secrets and grants, the registration access token included, in one unit of work
  ([ADR-1212](1212-deleting-a-client-resource-server-principal-or-tenant-removes-what-it-owns.md)).

### Who may register

- `registration_endpoint_allow_anonymous` (default `false`, merged with the boolean meet `And`, so a parent that
  disallows anonymous registration cannot be loosened below it) governs registration. When it is `false` the caller
  presents an initial access token as a Bearer credential, validated by the replaceable `IInitialAccessTokenValidator`.
  When it is `true`, registration is anonymous, the posture the conformance harness needs.
- A presented token is validated even where anonymous registration is allowed, so a scoped token is never silently
  ignored and an invalid one is refused (`401`).
- `POST api/tenants/{tenantId}/grants/initial-access-tokens` mints a hash-keyed `initial_access_token` grant, returns the
  plaintext once, returns the grant id for revocation through the grant management endpoint, and records an
  `InitialAccessTokenCreatedAuditEvent`. `lifetimeSeconds` defaults to one day and is at most thirty days (`400`
  otherwise), so `CreatedInitialAccessTokenResource.expiresWhen` always has a value. A grant without an expiry
  authorizes nothing.

### A token registers one client

- `IInitialAccessTokenValidator.ValidateAsync` returns the `InitialAccessTokenGrant` the token carries, or `null` when
  the token does not authorize registration, as it does for a spent grant (`PersistedGrant<T>.ConsumedWhen` set) or one
  without an expiry.
- `TryConsumeAsync` spends the token after every check has passed and immediately before the client is stored. A
  registration refused by an earlier check leaves the token unspent, so the caller can correct the request and present
  it again. A token that cannot be spent (already spent, expired or revoked) is `invalid_token` (`401`) and nothing is
  stored. A failure storing the client after the spend leaves the token spent: registration fails closed and an
  administrator mints another.
- The default spends the grant through `IPersistedGrantService.ConsumeOnceOrDefault`, not through `IExpiringKeySet`
  ([ADR-1164](1164-replicas-share-expiring-keys-values-and-indexes-through-ports-with-in-process-and-valkey-adapters.md)).
  `IExpiringKeySet` holds single-use state with no durable row of its own, such as a proof's `jti`. The token already
  has a row in the grant store, and a second record would have to agree with it. The grant row's concurrency token
  makes the spend atomic across replicas without a shared-state adapter: of two registrations presenting one token at
  once at most one succeeds, and the other is answered `invalid_token`
  ([ADR-1012](1012-concurrency-tokens-are-interceptor-managed-and-a-lost-race-surfaces-as-a-store-neutral-exception.md)).
- A custom validator implements `TryConsumeAsync` too and returns `false` when the token does not authorize
  registration.

### Binding a client to a resource server

- `CreateInitialAccessTokenRequest.resourceServerId` scopes a token to a resource server. Minting makes the checks the
  management API makes when it binds a client: the resource server exists in the tenant and is not a system resource
  server (`400`), and the caller is authorized to update it (`401` or `403`). The binding is stored on
  `InitialAccessTokenGrant.ResourceServerId` and reported on `CreatedInitialAccessTokenResource.resourceServerId`. An
  unscoped token registers ordinary clients.
- A client registered with a scoped token is bound to the token's resource server
  ([ADR-1168](1168-introspection-reports-a-token-active-only-to-the-party-that-consumes-it.md)). The resource server is
  checked again at registration, because it can be deleted or turned into a system resource server after minting; a
  token whose resource server does not qualify is `invalid_token` (`401`).
- A bound client must be confidential: `token_endpoint_auth_method` `none` is refused with `invalid_client_metadata`,
  and so is an update that would make a bound client public.
- A bound client may register `introspection_signed_response_alg`, `introspection_encrypted_response_alg` and
  `introspection_encrypted_response_enc` (RFC 9701 §6). They are validated like the `userinfo_*` metadata: an `*_enc`
  needs its `*_alg`, an encrypted response needs the client's `jwks` or `jwks_uri`, and each value must be among the
  tenant's `introspection_*_values_supported`. The response reports them. An ordinary client that registers them is
  refused with `invalid_client_metadata`, as introspection refuses it a JWT response.
- The client information response reports `resource_server_id` for a bound client. It is an extension the server sets:
  a request that carries it has it ignored like any unrecognized metadata (RFC 7591 §2), so a client that echoes its
  read response in an update does not fail.

## Options considered

- **Registration on the management API.** Rejected. That API is an operator surface under its own authorization
  ([ADR-1044](1044-the-management-api-authenticates-its-own-access-tokens-and-a-configured-client-bootstraps-the-first-globaladmin.md)),
  while RFC 7591 and 7592 are protocol endpoints a client calls for itself, advertised in discovery, with their own
  token authentication.
- **A dedicated store for registration access tokens.** Rejected. A per-client, hash-keyed, revocable bearer is a
  `PersistedGrant`. A parallel store would duplicate the grant store's tenant scoping, hash keying and EF plumbing and
  force a migration.
- **A metadata blob beside the settings.** Rejected. It would duplicate the functional fields and create two sources of
  truth.
- **Open registration by default.** Rejected. An anonymous write endpoint is not a safe baseline; a deployment opts in
  with a setting, and the merge lattice stops a child scope from re-enabling what a parent disallows.
- **Name the resource server in the registration request.** Rejected. The request carries no proof that its sender may
  act for the resource server. The token must carry that authority anyway, and a request member could then only agree
  with it or conflict with it.
- **Scope the token by the resource server's audience URI.** Rejected. Every other binding in the management API names
  the resource server by `resourceServerId`; the audience is written into tokens and is not the stored key.
- **Software statements (RFC 7591 §2.3).** Rejected. A signed statement needs a trust anchor per publisher, while the
  initial access token is already the authority the server issues and revokes.
- **Ignore a presented token where anonymous registration is allowed.** Rejected. A scoped token would register an
  ordinary client and nobody would be told.
- **Spend the token through `IExpiringKeySet`.** Rejected, for the reason under the decision: the grant row already
  carries single-use state.
- **Registration through the persisted-grant payloads, the client store and one endpoint family.** Chosen.

## Consequences

- Dynamic client registration and management work end to end with no schema change, and the server gains the Dynamic OP
  profile. The conformance harness can provision clients unattended with `registration_endpoint_allow_anonymous`
  enabled and run plan modules in parallel ([`docs/conformance-testing.md`](../conformance-testing.md)).
- `IInitialAccessTokenValidator` is the deployment seam for protected registration; a host plugs in its own policy, for
  example one that accepts an access token carrying a required scope.
- A deployment provisions an API's introspection client end to end: it creates the resource server, mints a token
  scoped to it, and the API registers its client with that token. Revoking an unused scoped token, or deleting its
  resource server, withdraws the authority it carried.
- A dynamically registered resource-server client chooses how its introspection responses are signed and encrypted, as a
  client created through the management API does.
- The Management console's mint dialog scopes a token to one of the tenant's non-system resource servers, and its
  one-time reveal names that resource server.
- A smell: if registered metadata ever needs first-class validation, indexing or a lifecycle apart from runtime
  settings, promote it into a dedicated client-metadata contract.
- Tests cover registration and management, token minting, single use and expiry, concurrent spends, scoped tokens and
  the refusal of public bound clients.
